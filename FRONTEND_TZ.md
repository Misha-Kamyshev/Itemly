# Техническое задание для FrontEnd

## 1. Контекст проекта

`Itemly` — сервис для публикации и просмотра изображений с тегами. Текущее готовое приложение реализовано на Android. Настоящее ТЗ описывает требования к FrontEnd-версии на основе фактической логики проекта.

ТЗ составлено по существующей реализации Android-клиента, поэтому в спорных местах приоритет у уже реализованного поведения.

## 2. Цель FrontEnd-версии

Нужно разработать веб-интерфейс, который повторяет основные пользовательские сценарии текущего приложения:

- регистрация и авторизация;
- просмотр основной ленты изображений;
- поиск изображений;
- просмотр детальной карточки изображения;
- лайк изображений;
- сохранение изображений в избранное;
- просмотр своих лайков;
- просмотр своих публикаций;
- просмотр профиля пользователя;
- просмотр профиля автора изображения;
- загрузка нового изображения;
- смена аватара пользователя;
- выход из аккаунта.

## 3. Предполагаемый стек FrontEnd

Рекомендуемый стек:

- `React` + `TypeScript`;
- `Next.js` или `Vite`;
- `React Router` или файловый роутинг;
- `TanStack Query` для серверного состояния;
- `Axios` или `fetch`-обёртка с interceptor/refresh logic;
- `Tailwind CSS`, `CSS Modules` или `SCSS`;
- `React Hook Form` + `Zod` для форм.

Допустим другой стек, если он покрывает все требования ниже.

## 4. Базовые требования к приложению

### 4.1. Тип приложения

SPA или SSR/Hybrid SPA с авторизованной зоной.

### 4.2. Язык интерфейса

Основной язык: русский.

### 4.3. Адаптивность

Интерфейс должен корректно работать:

- на мобильных устройствах;
- на планшетах;
- на десктопе.

### 4.4. Авторизация

Приложение должно иметь публичную и приватную зоны:

- неавторизованный пользователь видит только страницы входа и регистрации;
- авторизованный пользователь попадает в основное приложение.

## 5. Навигация и роутинг

### 5.1. Основные маршруты

Рекомендуемая структура маршрутов:

- `/auth/sign-in`
- `/auth/sign-up`
- `/`
- `/favorites`
- `/my-likes`
- `/profile`
- `/profile/:username`
- `/item/:id`
- `/search?q=...`
- `/upload`
- `/profile/change-avatar`

### 5.2. Поведение навигации

- После успешного входа или регистрации пользователь перенаправляется на главную страницу.
- При logout токены и данные пользователя удаляются, пользователь перенаправляется на страницу входа.
- Экран загрузки изображения и экран детального просмотра открываются как отдельные страницы или модальные сценарии. Для веб-версии предпочтительнее отдельные URL.

## 6. Пользовательские роли

В рамках текущего проекта используется одна роль: авторизованный пользователь.

Дополнительных ролей и админ-панели в существующей реализации нет.

## 8. Основные экраны

### 8.1. Экран входа

Поля:

- `login` — email или логин;
- `password`.

Элементы:

- кнопка `Войти`;
- ссылка `Нет аккаунта? Зарегистрируйтесь`;
- область отображения ошибки.

Правила:

- оба поля обязательны;
- при пустых полях показывать ошибку `Заполните все поля`;
- при серверной ошибке показывать `Ошибка сервера, попробуйте позже`;
- при сетевой ошибке показывать `Ошибка сети, попробуйте позже`.

После успешного входа:

- сохранить `username`, `email`, `access_token`, `refresh_token`;
- сохранить флаг авторизации;
- перевести пользователя в приватную часть приложения.

### 8.2. Экран регистрации

Поля:

- `username`;
- `email`;
- `password`;
- `passwordRepeat`.

Элементы:

- кнопка `Зарегистрироваться`;
- ссылка `Есть аккаунт? Войти`;
- область отображения ошибки.

Правила:

- все поля обязательны;
- `password` и `passwordRepeat` должны совпадать;
- при нарушении правил показывать:
  - `Заполните все поля`;
  - `Пароли не совпадают`;
- при серверной ошибке показывать `Ошибка сервера, попробуйте позже`;
- при сетевой ошибке показывать `Ошибка сети, попробуйте позже`.

После успешной регистрации:

- сохранить токены и данные пользователя;
- перевести пользователя в приватную часть приложения.

### 8.3. Главная страница

Содержимое:

- строка поиска;
- сетка изображений;
- pull-to-refresh аналог для веба: кнопка/жест не обязателен, но должен быть ручной механизм обновления;
- бесконечная прокрутка.

Поведение:

- по умолчанию загружается основной список изображений;
- поиск запускается с debounce `500 мс`;
- при пустой строке поиска снова показывается основной список;
- при вводе строки выполняется поиск;
- при скролле вниз подгружается следующая страница;
- клик по изображению открывает страницу изображения.

### 8.4. Страница избранного

Содержимое:

- заголовок `Вы сохранили`;
- сетка сохранённых изображений;
- empty state: `Вы ничего не сохраняли`.

Поведение:

- поддержка пагинации;
- поддержка ручного обновления;
- клик по карточке открывает страницу изображения.

### 8.5. Страница лайкнутых изображений

Содержимое:

- заголовок `Вы лайкнули`;
- сетка изображений;
- empty state: `Вы ничего не лайкали`.

Поведение:

- поддержка пагинации;
- поддержка ручного обновления;
- клик по карточке открывает страницу изображения.

### 8.6. Профиль текущего пользователя

Содержимое:

- обложка/шапка профиля;
- аватар;
- `username`;
- `email`;
- кнопка смены темы;
- кнопка выхода;
- сетка собственных публикаций;
- empty state: `Вы ничего не публиковали`.

Поведение:

- аватар загружается отдельным запросом;
- по клику на аватар открывается сценарий смены аватара;
- по клику на кнопку выхода выполняется logout;
- по клику на смену темы приложение циклически переключает режимы:
  - `system`;
  - `dark`;
  - `light`.

### 8.7. Профиль автора

Содержимое:

- аватар автора;
- `username`;
- сетка публикаций автора.

Отличия от профиля текущего пользователя:

- нет email;
- нет кнопки выхода;
- нет кнопки смены темы.

### 8.8. Страница изображения

Содержимое:

- большое изображение;
- кнопка назад;
- кнопка дополнительного меню;
- количество лайков;
- кнопка лайка;
- кнопка сохранения/удаления из избранного;
- имя автора;
- аватар автора;
- название изображения;
- список тегов;
- кнопка `Перейти в профиль`.

Поведение:

- при открытии страницы сначала загружается информация об изображении;
- ниже блока с основной информацией отображается список похожих изображений;
- похожие изображения подгружаются по тем же тегам;
- клик по тегу открывает страницу поиска по тегу;
- клик по автору или по кнопке перехода открывает профиль автора;
- лайк переключается без перезагрузки страницы;
- количество лайков обновляется сразу в UI;
- кнопка сохранения меняет текст:
  - `Сохранить`;
  - `Удалить`.

Дополнительное меню:

- `Скачать` — доступно всегда;
- `Удалить публикацию` — доступно только если текущий пользователь является автором изображения.

При удалении:

- показать диалог подтверждения;
- текст подтверждения: `Вы точно хотите удалить изображение для всех?`;
- после успешного удаления вернуть пользователя назад.

### 8.9. Поиск по тегу

Отдельный экран или маршрут на базе общего поиска.

Поведение:

- поле поиска заполнено выбранным тегом;
- ручное редактирование можно запретить, как в Android, либо разрешить и сделать полноценным поиском;
- загружаются изображения по запросу тега;
- работает пагинация;
- клик по изображению открывает карточку изображения.

### 8.10. Экран выбора изображения

Сценарий используется в двух режимах:

- публикация новой картинки;
- смена аватара.

Для web-версии допускается упрощение Android-логики:

- вместо доступа к системной галерее использовать `input type="file"` или drag-and-drop;
- камера может быть отдельной опцией, но не обязательна.

Требования:

- пользователь должен выбрать одно изображение;
- до выбора кнопка подтверждения скрыта или disabled;
- после выбора становится доступен переход дальше.

### 8.11. Экран публикации изображения

Содержимое:

- превью изображения;
- поле `Название`;
- динамический список тегов;
- кнопка `Добавить поле для тэга`;
- кнопка публикации;
- индикатор загрузки `Отправка фото…`.

Правила:

- название обязательно;
- минимум один тег обязателен;
- пустые теги не отправлять;
- пробелы внутри тега удалять;
- символ `#` в начале тега удалять перед отправкой;
- теги отправляются строкой через `;`.

Поведение:

- при попытке уйти со страницы без публикации показать подтверждение выхода без сохранения;
- после успешной публикации показать уведомление об успехе и закрыть экран;
- при ошибках показать сообщения сервера/сети.

### 8.12. Смена аватара

Сценарий использует тот же выбор изображения, что и загрузка публикации, но без экрана тегов и названия.

Поведение:

- пользователь выбирает изображение;
- отправляется запрос смены аватара;
- после успеха показать уведомление `Успешно`;
- вернуться назад;
- на странице профиля должен обновиться аватар.

## 9. Нижняя навигация

В приватной зоне нужна нижняя или боковая навигация со следующими пунктами:

- Главная;
- Избранное;
- Добавить;
- Мои лайки;
- Аккаунт.

Требования:

## 10. Список API

Базовый URL в текущем Android-проекте:

- `http://94.125.52.153:9698/`

### 10.1. Авторизация

`POST /user/signin`

Request:

```json
{
  "login": "string",
  "password": "string"
}
```

Response:

```json
{
  "username": "string",
  "email": "string",
  "access_token": "string",
  "refresh_token": "string"
}
```

`POST /user/signup`

Request:

```json
{
  "username": "string",
  "email": "string",
  "password": "string"
}
```

Response: аналогично `signin`.

### 10.2. Обновление токена

`POST /user/update_token`

Header:

- `Authorization: Bearer <refresh_token>`

Response:

```json
{
  "username": "string",
  "email": "string",
  "access_token": "string",
  "refresh_token": "string"
}
```

Требование:

- при `401` на защищённых запросах FrontEnd должен попытаться обновить access token;
- если refresh неуспешен, выполнить logout.

### 10.3. Аватар пользователя

`POST /user/get_image_user?username=<username>`

Response:

```json
{
  "path_preview": "string | null"
}
```

`POST /user/change_preview`

Multipart:

- `image`

Header:

- `Authorization: Bearer <access_token>`

### 10.4. Лента и изображения

`POST /items/get_main?last_id=<number|null>`

`POST /items/get_favorite?last_id=<number|null>`

`POST /items/get_my_image?last_id=<number|null>`

`POST /items/get_like?last_id=<number|null>`

`POST /items/get_items_author?last_id=<number|null>`

Header для всех:

- `Authorization: Bearer <access_token>`

Response:

```json
{
  "items": [
    {
      "id": 1,
      "image_url": "/path/to/image.jpg"
    }
  ],
  "has_next": true
}
```

### 10.5. Поиск

`POST /items/search_items`

Request:

```json
{
  "query": "string",
  "last_id": 123
}
```

Header:

- `Authorization: Bearer <access_token>`

Response: такой же, как у списков изображений.

### 10.6. Детальная информация об изображении

`GET /items/get_information?item_id=<id>`

Header:

- `Authorization: Bearer <access_token>`

Response:

```json
{
  "tags": ["tag1", "tag2"],
  "icon_author": "/path/to/avatar.jpg",
  "author": "string",
  "name": "string",
  "count_like": 0,
  "save_item": false,
  "like_item": false
}
```

### 10.7. Похожие изображения

`POST /items/get_similar_images`

Request:

```json
{
  "tags": ["tag1", "tag2"],
  "last_id": 123
}
```

Header:

- `Authorization: Bearer <access_token>`

Response: такой же, как у списков изображений.

### 10.8. Лайки и избранное

`POST /items/add_like?item_id=<id>`

`POST /items/delete_like?item_id=<id>`

`POST /items/save_item?item_id=<id>`

`POST /items/delete_favorite_item?item_id=<id>`

Header для всех:

- `Authorization: Bearer <access_token>`

### 10.9. Публикация изображения

`POST /items/add_item`

Multipart fields:

- `name_item`
- `tags`
- `image`

Header:

- `Authorization: Bearer <access_token>`

Формат `tags`: строка вида `tag1;tag2;tag3`.

### 10.10. Удаление изображения

`POST /items/delete_item?item_id=<id>`

Header:

- `Authorization: Bearer <access_token>`

## 12. Работа с токенами и local storage

Нужно хранить:

- `username`;
- `email`;
- `access_token`;
- `refresh_token`;
- флаг авторизации;
- выбранную тему.

Требования:

- при старте приложения проверять наличие валидной сессии;
- защищённые запросы отправлять с `Bearer access_token`;
- при `401` автоматически пробовать refresh;
- при провале refresh очищать сессию и перенаправлять на login.

## 13. Поведение списков и пагинации

Для всех списков изображений действуют единые правила:

- загрузка первой страницы при открытии;
- пагинация через `last_id`;
- если `has_next = false`, дальнейшие запросы не выполнять;
- при повторной загрузке первой страницы список должен заменяться полностью;
- при подгрузке следующей страницы новые элементы добавляются в конец;
- не допускать дубликатов карточек.

Списки:

- главная лента;
- результаты поиска;
- избранное;
- мои лайки;
- мои публикации;
- публикации автора;
- похожие изображения.

На основе Android-версии:

- полупрозрачный белый: `#50FFFFFF`;

Желательно сохранить визуальный характер:

- скругления;
- акцентные кнопки салатового цвета.

## 16. Состояния интерфейса

Для каждого экрана должны быть предусмотрены:

- `loading`;
- `success`;
- `empty`, если это список;
- `error`.

Дополнительно:

- disabled state кнопок во время запросов;
- optimistic update для лайка;
- моментальное обновление текста кнопки сохранения;
- индикатор публикации изображения.

## 17. Ошибки и уведомления

Базовые сообщения, которые уже используются в приложении:

- `Ошибка сервера, попробуйте позже`;
- `Ошибка сети, попробуйте позже`;
- `Заполните все поля`;
- `Пароли не совпадают`;
- `Название не может быть пустым`;
- `Добавьте хотя бы один тэг`;
- `Успешно`;
- `Сохранено в галерею`.

Для web-версии допустимы:

- toast;
- inline error;
- modal dialog.

## 18. Нефункциональные требования

- Код должен быть на `TypeScript`.
- Интерфейс должен быть адаптивным.
- Необходимо разделение на UI-компоненты и слой API.
- Все защищённые запросы должны идти через единый HTTP-клиент.
- Нужна обработка race condition для поиска.
- Нужна защита от повторной отправки формы.
- Изображения должны быть lazy-loaded.
- Для списков изображений желательно использовать skeleton/loading placeholders.

## 19. SEO и метаданные

Минимальные требования:

- корректный `title` для основных страниц;
- `meta description` хотя бы для публичных экранов;
- Open Graph для страницы изображения желательно, если выбран SSR/Next.js.

## 20. Аналитика и логирование

В текущем Android-проекте аналитика отсутствует. Во FrontEnd можно заложить точки расширения, но как обязательное требование это не фиксируется.

## 21. Критерии приёмки

FrontEnd считается готовым, если:

- пользователь может зарегистрироваться и войти;
- сессия сохраняется после перезагрузки страницы;
- при истечении access token происходит refresh;
- пользователь видит главную ленту;
- работает поиск по строке;
- работает открытие карточки изображения;
- можно лайкать и убирать лайк;
- можно сохранять изображение и удалять из избранного;
- доступны страницы избранного, лайков и профиля;
- в профиле отображаются собственные публикации;
- работает просмотр профиля автора;
- можно загрузить новое изображение с названием и тегами;
- можно сменить аватар;
- автор может удалить свою публикацию;
- реализованы empty/loading/error states;
- UI корректно работает на мобильном и десктопном разрешении.

## 22. Ограничения и допущения

Ниже перечислены моменты, которые явно не раскрыты в Android-клиенте и требуют подтверждения у заказчика или backend-команды:

- точные тексты ошибок backend помимо общих сообщений;
- требования к форматам изображений и лимитам размера файла;
- нужна ли публичная веб-доступность карточек без авторизации;
- нужен ли SSR для страниц изображений;
- нужен ли drag-and-drop и доступ к камере в браузере;
- должна ли веб-версия полностью повторять мобильную нижнюю навигацию или допустим desktop sidebar.

## 23. Рекомендуемая структура FrontEnd-проекта

```text
src/
  app/
  pages/ or routes/
  widgets/
  features/
  entities/
  shared/
    api/
    ui/
    lib/
    config/
```

Минимально должны быть выделены:

- слой API;
- слой авторизации;
- слой работы с изображениями;
- слой профиля;
- слой переиспользуемых UI-компонентов.

## 24. Итог

FrontEnd должен воспроизвести готовую бизнес-логику Android-приложения `Itemly` в веб-формате, не меняя ключевые пользовательские сценарии: авторизация, лента, поиск, карточка изображения, лайки, избранное, профиль, публикация и управление аватаром.
